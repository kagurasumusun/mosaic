# 0018: IA-32 は Unicorn の 16/32 ビットバックエンドで実行する

状態: 初期実装を採用。x86 全体を実装したとはみなさない。

根拠: 設計書 §12.1、ADR 0001、ADR 0007、ADR 0009、ADR 0019。

## 背景

PC の起動は実モードの 16 ビットコードから始まり、ローダやカーネルが
保護モードへ移る。CPU を自前で書かないという制約（ADR 0007）のもとでは、
Unicorn の 1 インスタンスでこの遷移を越えられるか、越えられないなら何を
アダプタが担うのかを先に決める必要がある。実測で分かったことは次の 4 点。

1. `MODE_16` と `MODE_32` は初期状態の違いでしかない。ゲストが `CR0.PE` と
   `LGDT` を書けば同じインスタンスが保護モードで動く。エンジン側から
   `CR0` を書いてモードを切り替える経路は用意しない。
2. `EIP` の読み書きはセグメント相対のオフセットである。`CS` のベースは
   命令フェッチとデータアクセスの両方に効くが、`uc_reg_write(CS)` で
   セレクタを書いてもベースは設置されない（実測: `CS=07C0h, EIP=0` で
   `7C00h` ではなく `8400h` 付近を実行した）。`JMP FAR` は正しくベースを
   設置する。したがって起動点は `JMP FAR` スタブで入る（ADR 0019）。
3. `INT n` は Unicorn 自身が IVT/IDT を読んでフレームを積まない。
   `UC_HOOK_INTR` に通知して停止し、ハンドラが答えなければ
   `UC_ERR_EXCEPTION` になる。IVT 配送はアダプタの仕事である。
4. `GDTR`/`IDTR` の 10 バイト読み出しは壊れている（ADR 0007 の追記）。
   `LGDT`/`LIDT` の実行を観測して記録する。

## 決定

- `Backend::X86Real`（`MODE_16`）と `Backend::X86Protected`（`MODE_32`）を
  `UnicornX86` に足す。どちらも `CpuEngine` の同じ契約を満たす。
- ポート I/O は `PortBus` に集約する。`IN`/`OUT` は 1/2/4 バイトの
  1 トランザクションとして渡し、未接続ポートは `0xFF` を返す。PIC・PIT・
  RTC・UART はこのポートの向こう側に置き、CPU エンジンは番地を知らない。
- 外部割り込みは量子境界で配送する。`EFLAGS.IF` が 0 の間はキューに残す。
  フレームは実モード 6 バイト、32 ビットゲート 12 バイトで、割り込み
  ゲートのみ `IF` を落とす（Intel SDM Vol.3 Table 6-2）。
- `LGDT`/`LIDT` は命令フックで復号して記録する。5 バイト未満の命令は
  復号しないので実モードの短い命令は素通りする。
- 未処理のソフトウェア割り込みはサービスに渡す（ADR 0019）。サービスが
  答えない場合に限り、アダプタが IVT/IDT からゲートを読んで自分で積む。

## 受け入れ基準

- 実モードの `INT` が 6 バイトフレームを積み、`IRET` で戻る。
- 32 ビットゲートの `INT` が 12 バイトフレームを積み、`IF` が落ちる。
- `IN`/`OUT` がポートバス上で幅を保った 1 アクセスである。
- 実モードのゲストが `JMP FAR` の後、`CS` ベース相対でデータを読み書きできる。

## まだ主張しないこと

- セグメント記述子の全属性、ページング、タスクゲート、`SYSENTER`。
- `MODE_16` インスタンスで `CR0` を書く経路（実測で失敗する）。
- 実測していない CPU 例外（`#GP`/`#PF` など）のフレーム内容。
